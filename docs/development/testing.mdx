# Тестирование

В проекте используется **pytest** — гибкий фреймворк для тестирования Python-приложений.

Он подходит для различных уровней тестирования:

- **Unit-тесты** — проверка отдельных функций и классов.
- **Integration-тесты** — проверка взаимодействия компонентов, например сервисов и базы данных.
- **Functional/API-тесты** — проверка бизнес-сценариев через API.
- **E2E-тесты** — проверка полного пользовательского сценария через браузер.
- **Performance-тесты** — проверка производительности с помощью дополнительных инструментов и плагинов.

В SwingTraderAI pytest используется прежде всего для тестирования Python backend.

## Структура тестов

Тесты проекта находятся в отдельной директории:

```text
tests/
````

Конфигурация pytest находится в:

```text
pyproject.toml
```

В проекте также используется `pytest-asyncio`, поскольку backend построен на асинхронном Python-стеке.

## Запуск тестов

Для запуска всех тестов:

```bash
poetry run pytest
```

При использовании Docker тесты также могут запускаться через отдельное тестовое окружение:

```bash
docker-compose -f docker-compose.yml -f docker-compose.test.yml up --abort-on-container-exit
```

## Базовая концепция pytest

В pytest тест обычно представляет собой обычную Python-функцию с именем, начинающимся с `test_`.

Например:

```python
def test_addition():
    result = 2 + 2

    assert result == 4
```

Здесь:

* `test_addition` — тестовая функция;
* `result` — результат выполнения проверяемого кода;
* `assert` — проверка ожидаемого результата.

Если условие `assert` не выполняется, pytest показывает подробную информацию о том, что именно отличается от ожидаемого результата.

# Фикстуры pytest

**Фикстуры (`fixtures`) — один из самых важных механизмов pytest.**

Фикстура используется для подготовки данных или ресурсов, которые нужны тесту.

Проще говоря, вместо того чтобы в каждом тесте заново создавать пользователя, подключение к базе данных, HTTP-клиент или тестовые данные, мы один раз описываем способ их создания в фикстуре и затем передаём фикстуру в нужные тесты.

## Простой пример

```python
import pytest


@pytest.fixture
def number():
    return 10


def test_number(number):
    assert number == 10
```

Здесь:

1. pytest видит функцию `number`, отмеченную `@pytest.fixture`;
2. перед запуском `test_number` создаёт значение фикстуры;
3. передаёт результат в аргумент `number`;
4. тест использует готовое значение.

То есть pytest автоматически выполняет **внедрение зависимости**.

```text
Fixture
   ↓
pytest
   ↓
test_number(number)
```

Тесту не нужно самостоятельно вызывать `number()`.

## Почему фикстуры важны

Фикстуры особенно полезны для SwingTraderAI, потому что backend использует:

* PostgreSQL;
* Redis;
* асинхронные SQLAlchemy-сессии;
* FastAPI;
* API-клиенты;
* пользователей;
* рыночные данные;
* тикеры;
* ML-компоненты.

Например, вместо создания подключения к базе данных внутри каждого теста можно создать фикстуру:

```python
@pytest.fixture
async def db_session():
    ...
```

После этого любой тест, которому нужна база данных, может получить её через аргумент:

```python
async def test_create_ticker(db_session):
    ...
```

Это делает тесты короче и уменьшает количество повторяющегося кода.

# Жизненный цикл фикстур

Фикстуры могут иметь различный `scope`, то есть различную продолжительность жизни.

Основные варианты:

| Scope      | Время жизни                    |
| ---------- | ------------------------------ |
| `function` | Создаётся для каждого теста    |
| `class`    | Один раз для тестового класса  |
| `module`   | Один раз для файла с тестами   |
| `session`  | Один раз на весь запуск pytest |

По умолчанию используется:

```python
@pytest.fixture(scope="function")
```

Это означает, что для каждого теста создаётся отдельный экземпляр фикстуры.

## Пример `scope`

```python
@pytest.fixture(scope="session")
def application():
    ...
```

Такая фикстура создаётся один раз за весь запуск тестов.

Это удобно для дорогих операций, например подготовки общего окружения.

Однако данные, которые могут изменяться во время теста, обычно лучше создавать на уровне `function`, чтобы тесты не зависели друг от друга.

# Setup и teardown

Фикстуры могут не только создавать ресурсы, но и освобождать их после завершения теста.

Для этого используется `yield`.

```python
@pytest.fixture
def resource():
    resource = create_resource()

    yield resource

    resource.close()
```

Логика здесь следующая:

```text
create_resource()
       ↓
     yield
       ↓
     тест
       ↓
resource.close()
```

Всё, что находится до `yield`, выполняется перед тестом.

Всё, что находится после `yield`, выполняется после теста.

Это особенно полезно для:

* подключения к базе данных;
* временных файлов;
* HTTP-клиентов;
* тестовых пользователей;
* Redis-соединений;
* браузерных контекстов.

# Фикстуры как Dependency Injection

Фикстуры pytest можно рассматривать как простой механизм **Dependency Injection**.

Например:

```python
@pytest.fixture
def user():
    return User(
        email="test@example.com",
        role="user",
    )


def test_user_role(user):
    assert user.role == "user"
```

Тест сообщает pytest:

```text
Мне нужен user.
```

Pytest находит фикстуру `user`, выполняет её и передаёт результат в тест.

Это особенно удобно в больших проектах, где один и тот же набор зависимостей используется большим количеством тестов.

# `conftest.py`

Общие фикстуры обычно размещаются в файле:

```text
tests/conftest.py
```

Pytest автоматически обнаруживает `conftest.py` и делает находящиеся в нём фикстуры доступными тестам соответствующего уровня.

Например:

```python
# tests/conftest.py

@pytest.fixture
async def client():
    ...
```

После этого в тестах можно использовать:

```python
async def test_healthcheck(client):
    response = await client.get("/health")

    assert response.status_code == 200
```

Не требуется импортировать `client` из `conftest.py`.

Именно это делает `conftest.py` удобным местом для общих тестовых зависимостей.

# Параметризация

`@pytest.mark.parametrize` позволяет запускать один тест с несколькими наборами данных.

Например:

```python
@pytest.mark.parametrize(
    "value,expected",
    [
        (1, 2),
        (2, 4),
        (5, 10),
    ],
)
def test_double(value, expected):
    assert value * 2 == expected
```

Вместо написания трёх отдельных тестов pytest выполнит один тест несколько раз с разными значениями.

Для торговой системы это удобно, например, при проверке:

* разных тикеров;
* разных таймфреймов;
* различных значений индикаторов;
* разных торговых сигналов;
* различных рыночных сценариев.

# Маркеры

В проекте определены следующие маркеры:

* `asyncio`
* `slow`
* `db`

Они указаны в конфигурации pytest в `pyproject.toml`.

Маркеры позволяют классифицировать тесты.

Например:

```python
@pytest.mark.slow
def test_large_dataset():
    ...
```

После этого можно запускать только определённую категорию тестов.

Например, пропустить медленные тесты:

```bash
poetry run pytest -m "not slow"
```

Или запустить только тесты базы данных:

```bash
poetry run pytest -m db
```

# Асинхронные тесты

Поскольку проект использует FastAPI и асинхронный SQLAlchemy, часть тестов является асинхронной.

Для этого используется `pytest-asyncio`.

Пример:

```python
@pytest.mark.asyncio
async def test_database_operation(db_session):
    result = await some_database_operation(db_session)

    assert result is not None
```

В конфигурации проекта также установлен режим:

```toml
asyncio_mode = "auto"
```

Это упрощает работу с асинхронными тестами.

# Производительность

Сам pytest не является полноценным инструментом нагрузочного тестирования.

Для измерения производительности можно использовать дополнительные инструменты:

* `pytest-benchmark` — микробенчмарки;
* `pytest-xdist` — параллельный запуск тестов;
* Locust — нагрузочное тестирование;
* k6 — нагрузочное тестирование API.

Например, `pytest-benchmark` позволяет измерять время выполнения конкретной операции:

```python
def test_indicator_performance(benchmark):
    result = benchmark(calculate_indicators)

    assert result is not None
```

Для performance-тестов рекомендуется использовать отдельный маркер:

```python
@pytest.mark.performance
def test_api_latency():
    ...
```

# Frontend и E2E

Pytest не является frontend-тестовым фреймворком для React.

Для React-компонентов обычно используются инструменты JavaScript/TypeScript-экосистемы, например:

* Vitest;
* Jest;
* Playwright;
* Cypress.

При этом pytest можно использовать для браузерных E2E-тестов вместе с Playwright для Python.

Например:

```python
def test_login(page):
    page.goto("http://localhost:5173/login")

    page.fill("#email", "test@example.com")
    page.fill("#password", "password")

    page.click("button[type=submit]")

    expect(page).to_have_title("Dashboard")
```

В таком сценарии pytest выступает тестовым runner'ом, а Playwright управляет браузером.

# Полезные практики

Для проекта рекомендуется придерживаться следующих принципов:

* **Arrange → Act → Assert** — подготовка данных, выполнение действия, проверка результата.
* Каждый тест должен быть максимально независимым от других тестов.
* Общие зависимости следует выносить в fixtures.
* Тестовые данные следует создавать через fixtures или factories.
* Медленные тесты необходимо помечать `slow`.
* Integration-тесты с PostgreSQL следует отделять от быстрых unit-тестов.
* Асинхронный код тестировать через `pytest-asyncio`.
* Для mock-объектов использовать `pytest-mock`.
* Для покрытия кода использовать `pytest-cov`.
* Для параллельного выполнения использовать `pytest-xdist`.

## Статус реализации

Репозиторий содержит полноценную инфраструктуру pytest:

* конфигурацию в `pyproject.toml`;
* директорию `tests/`;
* асинхронный режим через `pytest-asyncio`;
* тестовые маркеры;
* настройки coverage;
* отдельные настройки для тестового окружения.

При этом наличие тестовой инфраструктуры не означает, что каждый runtime-сценарий приложения полностью покрыт автоматическими тестами.

Корректнее считать pytest **основой тестового контура Python backend**, который предназначен для проверки отдельных компонентов, интеграций и ключевых бизнес-сценариев приложения.
